# handoff — the launch

How `handoff` launches the next session and what the brief's Reporting section carries, where the `session-launch` binding reads filled; "the contract" is `.claude/references/core/trees-contract.md`.

## The launch

After the brief is written, this session launches the next one where all four conditions below hold; where any fails, nothing is launched, and `## What you show me` gives the paste line. The target is the tree the next session opens in, as the brief's Context names it: where `trees` is filled, the branch's own tree by its path per the List read, or the hub; where it reads absent, the project root.

1. **A handoff point** — the human invoked this skill or asked for this handoff, or ordered the branch opened for which `g0-open` (for one item or a set) or `tackle-issue` invokes this skill, or this session reached a handoff point of `## When to hand off` and invoked this skill itself; and the human did not say they will open the session themselves. The Launch command's permission prompt is the human's check: nothing is asked before it.
2. **The slots** — this session's `session-launch` binding reads filled with its Launch command, List command and Confirm window, and the target's with its Hub session name, read as `handoff` `## Bindings` says, each as the contract reads it, and the `verification` binding carries its *Path form*; one missing or `none` is named with the paste line.
3. **Not the hub** — where `trees` is filled, the target is not the hub: a second session there would be a second writer in the hub's one tree.
4. **A plain-ASCII prompt** — the paste line's text, the file's absolute path written in, is plain ASCII.

The steps, in order: HANDOFF, its own `SendMessage`, first; then BEFORE, RUN and CONFIRM as one Bash call; then LAST ACT.

1. **HANDOFF** — only where the target is this session's own project root — its own tree, or the project root where `trees` reads absent — a hand-off launch: one line by `SendMessage` to this project's Hub session name, `HANDOFF - <branch>; lane: <lane>; brief <file name>`, `<branch>` this session's branch, `<lane>` the Lane of the brief this session has just written, and `<file name>` the brief's file name, not its path. A launch into another tree sends nothing.
2. **BEFORE** — the call's first command, `py scripts/hub.py sessions-at "<tree>" > "<record>\before.txt"`, with `--vacant` added before the `>` where the target is not this session's project root: the List command read once, and the sessions at the target printed, each line ending in its full id, into `<record>\before.txt` by the shell's redirect. A session is at the target when its working directory, as the list shows it, is the target's path or lies under it, compared as the trees contract (`.claude/references/core/trees-contract.md`) compares paths. Where the target is not this session's project root and a session is at it → no launch: one line saying that tree has a session running, then the paste line.
3. **RUN** — chained to BEFORE by `&&` and grouped with CONFIRM in one `{ …; }`, so `--vacant`'s exit 3 skips both: the Launch command as bound, its `<tree>` the target's path in the `verification` binding's *Path form*, its `<branch>` the branch the next session works on, and its `<prompt>` the paste line's text; then `; rc=$?` keeps its exit status, and `; cd "<root>"` returns the shell to this session's project root whatever that status, since the Bash tool keeps its working directory between calls; then `&& [ "$rc" -eq 0 ]`, so a Launch command that errored ends the call there, CONFIRM not run, and the call exits non-zero with no `hub.py sessions-at:` line.
4. **CONFIRM** — inside RUN's group, chained to that status test by `&&`: `py scripts/hub.py sessions-at "<tree>" --since "<record>\before.txt" --wait <seconds>`, `<seconds>` the `session-launch` binding's *Confirm window* in seconds, which re-reads the List command until a session at the target appears whose full id ends no line of the file BEFORE wrote. It appears → one line: the branch launched, and its tree. The Launch command errored, or the window passed, each told by the call's exit and output below → one line naming which and telling the human to check the session list before opening a session there, then, on a hand-off launch, one line by `SendMessage` to the same hub, `BLOCKED - <branch>; lane: <lane>; launch failed`, `<branch>` and `<lane>` as HANDOFF's; then the paste line; the tree is kept.
5. **LAST ACT** — where the target is this session's project root — its own tree, or the project root where `trees` reads absent: the launch, confirmed or not, ends this session's work, and it takes no further step, so one writer per tree holds. It sends nothing and stays listed until the hub stops it, when the successor's `STARTED` names it, as `close-tree` `## A handed-off session` says, or the human closes it, or the tree's close stops every session there.

The one call, whole, `<record>` the record directory `handoff` `## The dated note` names, which the drafts' Writes made where `trees` is filled — where `trees` is absent, `.scratch/handoff-<slug>-record/` under the project root, `<slug>` the brief's, which no draft made, so the call opens with `mkdir -p "<record>" &&` there, the redirect making no directory — and `<root>` this session's project root, every path in the *Path form*:

```
py scripts/hub.py sessions-at "<tree>" [--vacant] > "<record>\before.txt" && { <the Launch command>; rc=$?; cd "<root>" && [ "$rc" -eq 0 ] && py scripts/hub.py sessions-at "<tree>" --since "<record>\before.txt" --wait <seconds>; }
```

Its exit and output are read so:

- Exit 3 — BEFORE wrote a session at the target into `<record>\before.txt` under `--vacant`, so neither RUN nor CONFIRM ran → step 2's no-launch line and the paste line. Only BEFORE exits 3: a Launch command's own exit, 3 or any other, ends the group at its status test, which exits 1.
- A non-zero exit with the line `hub.py sessions-at: no new session at <tree> within <n>s` — `--wait` passed the window → step 4's failure line naming the window, then, on a hand-off launch, its `BLOCKED` message, then the paste line; the tree is kept.
- Any other non-zero exit, with no such line — the Launch command errored, CONFIRM not run, or, where a `hub.py sessions-at:` line names a List read that failed, BEFORE or CONFIRM could not read the list → step 4's failure line naming the launch error, or that read, then, on a hand-off launch, its `BLOCKED` message, then the paste line; the tree is kept.
- Exit 0 — `--wait` printed the new session's line → step 4's one line.

So, after the drafts' Writes of `handoff` `## The dated note`, issued together in one message, a hand-off into this session's own tree takes three calls — the placing call, HANDOFF and the launch call — plus the `BLOCKED` message only on a failure; a launch brief into another tree two, the placing call and the launch call; and a brief for the hub one, the placing call. Where `trees` is absent there are no drafts and no placing call: the brief stays a Write under `memory/handoffs/`, the write guard's watched route (`.claude/references/core/hooks.md` `## What the write guard's handoff rule refuses`), the session id a shell read, and the dated note this session's own re-read and append, so a hand-off there takes at least five calls — the brief's Write, the session-id shell read, the note's re-read and append, one call or more, HANDOFF and the launch call — plus the `BLOCKED` message only on a failure.

## Reporting

The text below, written into the brief in plain ASCII, with `<hub session name>` the target's Hub session name, `<branch>` and `<lane>` the next session's branch and the brief's Lane, written out, and `<predecessor>`, on a hand-off into this session's own root, left in the brief as it stands where `trees` is filled, for the placing call's `--predecessor` to replace by a space and `followed by "; predecessor <session id>"`, `<session id>` this session's id whole, or to remove where none is set, and, where `trees` is absent, replaced so by this session with the id `handoff` item 9 read, or removed where none was; otherwise it is removed as the brief is drafted; `<EVENT>`, `<detail>` and `<commit>` stay as they stand.

```
Report to the hub session `<hub session name>` by SendMessage, one plain-ASCII line per event, in the form `<EVENT> - <branch>; lane: <lane>; <detail>`. STARTED: your first act, before anything else; detail the skill named in Next steps<predecessor>. BLOCKED: whenever you stop on something only the human or the hub can clear; detail what blocks you. FINISHED: at once when the human declines this item at its G0 scope, detail `declined at G0, nothing written`; otherwise after the merge and close-out, detail `merged <commit>` - g1-lock, g2-accept and g2-lite send it at their REMOVE step, and where your closing skill has none, send it yourself after the close-out. The hub never replies and never gives you work: do not wait for an answer.
```
