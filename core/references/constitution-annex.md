# Constitution annex

The sections below are constitution text, moved here verbatim so the constitution loaded into every session stays short; each keeps its heading in the constitution with a one-sentence pointer to this file, and `## The amendment rule` keeps its first sentence there. They remain the constitution's: they change only on a `design-` branch of the base repo, through the design workflow, locked by the human at G1, and they read as they read in the constitution — "the constitution" and "a project's copy" mean what they meant there. `## Invariants and their enforcers`, at the end, is not constitution text: it catalogues each rule of the constitution, this file's moved text included, with what enforces it today, and is corrected whenever an enforcer is added, renamed or removed — nothing checks that, so the register's own upkeep is advice.

## Agent and skill contracts

Agent files are tool-native: `name`, `description` (with the "use when" trigger), `tools`, `model`, `status`. Least privilege is structural — a reviewer without Write cannot write, whatever the prompt drifts into.

- **Bash is granted only to an agent that must run something** — a build, a version-control read, a reproduction. "read-only Bash" is not a tool category, Glob, Grep, and Read cover find, grep, wc, and ls.
- **Write and Edit go only to an agent whose deliverable is a file**, and its body names the single path prefix it may write under.

Each pack declares its own agents' tool rows in its `PACK.md`; the core tool-allowlist reference states the two rules and the role patterns, and the constitution states the two rules, never the table.

No absolute paths; pack references are addressed as `.claude/references/<pack>/…`.

Every agent body carries an `## Output` heading whose first non-blank line reads ``First line: `<STATUS> — <brief path or task>`, where STATUS is DONE | PARTIAL | BLOCKED | NO-BINDING.``

A skill declares `kind`, `agents`, `stops`, the bindings it consults, and a graceful-degradation path when a binding or an agent is missing. A dispatch to a roster agent whose `tools:` include Write, Edit or Bash names an existing **brief file** under the scratch area, and the agent guard denies one that does not; a read-only roster agent may take its brief inline, and the report filer files its report under the scratch area's reports folder. A skill whose own step files a brief for a fan-out keeps it and passes its path; the agent's report is the up half of the delegation contract.

## Pack, preset, and manifest contracts

The pack is the unit of validation, promotion, and upgrade; the manifest is the source of truth for a project's toolset; a preset is a named pack list and nothing more — it is sugar for the composer and a regression fixture for the validator, never a directory of its own.

A pack is a directory with a `PACK.md` whose frontmatter is the contract: `name`, `kind`, `version`, `status`, `removal-date`, `description`, `triggers`, `requires`, `conflicts`, `provides` (agents, skills, references, preflight-checks), `roles` (one tool row per agent the pack provides), and `bindings` (key, file, required, interview). These fields exist so the validator can check closure without parsing prose.

A project's manifest records `harness`, `base`, `preset`, `packs`, `parent`, `files`, and `bindings`. The `files` ledger records what was copied and from which pack version. Anything under `.claude/agents` or `.claude/skills` **not** in the ledger is local by definition.

Projects own their copies. An upgrade never silently overwrites a locally modified file; a local modification is the seed of a promotion.

## Lifecycle statuses and `removal-date`

Packs, skills, and agents carry a status: `draft | active | deprecated`. A thing that is deprecated carries a `removal-date`.

**Preserve over delete.** Status fields and `removal-date` on packs, skills, agents. Nothing vanishes without a re-introduction path.

A deprecated item still in use is a validator warning naming its `removal-date`, not a failure.

## The promotion rule

A local (unledgered) file is promoted by copying it into the base repo on a `promote-<slug>` branch, into an existing pack or a new pack directory whose `PACK.md` starts at `status: draft`. The human reviews it in the base repo with the harness's own workflow. After merge and a version bump the originating project upgrades: its copy now matches the pack file, the ledger adopts it, and it stops being local.

Promotion is always explicit and human-run.

## The amendment rule

A project's copy is LOCKED: it is replaced on upgrade and is never edited in place, so a disagreement with the constitution is an amendment or a binding, never a local patch.

## Invariants and their enforcers

Each row below names one rule of the constitution or of this file's moved text, paraphrased; where it lives, by file and heading; its Kind; and its Enforcer, by durable address. The Kind is one of four: `hook`, a hook a composed settings template registers; `validator`, a `validate` check, a `doctor` row or a unit test the verification binding runs, a script's behaviour that such a test pins included, a check that only warns saying "a warning"; `prose`, a skill step or declared stop, an agent body, a gate or a review, followed by judgment; `advice`, where nothing holds the rule. Where a rule's clauses are held by different enforcers, the row's Kind is the weakest holder among its clauses, in the order hook, validator, prose, advice, and the Enforcer cell names every stronger clause's holder. A partial guard is a check that covers only part of a clause: it is named in the Enforcer cell with what it leaves, and it never sets the Kind. Another pack's enforcer is named by its role, or a skill by its own name and step, and counts where that pack is composed; an enforcer the design intends but has not built is marked "(design intent, not yet built)" and never sets the Kind.
